# 기상 API 호출 예산

이 문서는 30분 기상 배치가 사용하는 공급자별 요청 수를 계산하는 기준 문서다. 호출 수는 반드시 대상자 위치에서 계산하며, 쉼터 위치를 HRI 기상 조회 키로 사용하지 않는다.

- 문서 유형: reference
- 산정 기준일: 2026-08-23 KST
- 관련 계약: [외부 API 계약](./external-contracts.md), [구현 계획의 호출량 결정](../구현계획.md#23-api-호출량-계산-오류)
- 비밀정보 정책: API 키, 전체 요청 URL, 이름·주소·연락처를 기록하지 않는다.

## 1. 확정 결론

| 항목                                |            확정값 |
| ----------------------------------- | ----------------: |
| 배치 간격                           |              30분 |
| 하루 실행 슬롯 `R`                  | `1,440 / 30 = 48` |
| 가상 대상자 수 `N`                  |                 5 |
| 고유 APIHub 500m 조회 지점 `U500`   |                 5 |
| 고유 단기예보 5km 격자 `U5`         |                 3 |
| APIHub 정상 운영 호출               |          288회/일 |
| APIHub 모든 요청 1회 재시도 상한    |          576회/일 |
| 공공데이터포털 폴백 호출 상한       |          144회/일 |
| 공공데이터포털 폴백 1회 재시도 상한 |          288회/일 |

APIHub의 현재 계정 화면에는 매일 00시 초기화되는 **20,000회/일** 한도가 표시돼 있다. 정상 운영 288회는 한도의 1.44%, 모든 요청이 한 번씩 재시도되는 576회는 2.88%다. 따라서 요청 횟수 기준으로는 각각 19,712회와 19,424회의 여유가 있다.

공공데이터포털의 계정별 일 한도는 현재 저장소나 제공된 계정 화면에서 확인되지 않았다. 필요한 최소 예산은 폴백 기준 144회/일, 한 번 재시도를 허용하면 288회/일이며, 의약품 요청 예산은 이 수치에 별도로 더해야 한다.

## 2. 대상자와 격자 근거

현재 [목 데이터](../src/lib/mock/data.ts)의 대상자는 12명이다. P0-08과 이후 5명 시드의 재현성을 위해 안정 ID 오름차순의 첫 5명(`s-001`~`s-005`)을 기준 집합으로 고정한다. 아래 좌표는 모두 데모용 가상 좌표이며 실제 사용자의 위치가 아니다.

| 가상 ID |    위도 |     경도 | 단기예보 `nx` | 단기예보 `ny` | 5km 그룹 |
| ------- | ------: | -------: | ------------: | ------------: | -------- |
| `s-001` | 35.8281 | 128.6321 |            89 |            90 | A        |
| `s-002` | 35.8404 | 128.6215 |            89 |            90 | A        |
| `s-003` | 35.8632 | 128.5910 |            89 |            90 | A        |
| `s-004` | 35.8419 | 128.5566 |            88 |            90 | B        |
| `s-005` | 35.8815 | 128.5602 |            88 |            91 | C        |

### 2.1 APIHub 500m 조회 지점

APIHub 운영 계약은 `sfc_nc_var.php`의 **특정 지점 다중요소** 호출이다. 한 지점의 `ta_chi`, `ta`, `hm`을 한 요청으로 받으므로 요소가 세 개여도 호출 수는 한 번이다.

다섯 좌표의 쌍별 Haversine 거리 중 최솟값은 `s-001`과 `s-002` 사이의 약 1,668m다. 이는 500m 정사각 격자의 최대 대각선 약 707m보다 크므로 두 좌표가 같은 500m 셀에 들어갈 수 없다. 따라서 현재 대상자 집합의 고유 500m 조회 지점은 정확히 5개다.

운영 ETL에서 APIHub 위·경도 배열로 실제 격자 인덱스를 만들게 되면 그 인덱스를 최종 캐시 키로 사용한다. 격자 인덱스가 아직 없는 상태에서 위·경도를 소수점 자릿수로 임의 반올림해 합치면 안 된다.

### 2.2 단기예보 5km 격자

단기예보 격자는 KMA DFS Lambert 변환 상수(`GRID=5`, `SLAT1=30`, `SLAT2=60`, `OLON=126`, `OLAT=38`, `XO=43`, `YO=136`)로 계산했다. 결과 집합은 `(89,90)`, `(88,90)`, `(88,91)`이므로 고유 격자는 3개다.

`getVilageFcst` 한 응답에서 `TMP`와 `REH`를 함께 필터링한다. 카테고리별로 API를 두 번 호출하지 않는다.

### 2.3 쉼터가 계산에서 제외되는 이유

원천 `무더위쉼터.dbf`는 950개 레코드와 `geoIdn`, `resultType`, `x`, `y` 등의 필드를 가진다. DBF의 `x`, `y`는 WGS84 좌표지만 SHP 도형은 `Korea_2000_East_Belt_2010` 투영 좌표다. 반면 현재 목 `Shelter.x`, `Shelter.y`는 지도처럼 보이게 하기 위한 0~100 상대 좌표라 기상 격자 계산에 사용할 수 없다.

쉼터 950곳은 추천·반경 조회용 정적 마스터이고 HRI 환경값은 대상자 위치에 붙는다. 따라서 상세서의 과거 가정인 `쉼터 38격자 × 48회 = 1,824회/일`은 이 배치의 입력이 아니다. 1,824회는 과거에 적힌 1,000회 한도도 초과하므로 해당 최적화 설명을 구현 근거로 사용하지 않는다.

## 3. 공급자별 계산식

다음 기호를 사용한다.

```text
R    = 하루 배치 슬롯 수 = 48
U500 = 고유 500m 대상자 조회 지점 = 5
U5   = 고유 단기예보 5km 격자 = 3
P    = 500m 지점 다중요소 endpoint 수 = 1
W    = 전국 특보 endpoint 수 = 1
F    = 실제 폴백이 실행된 슬롯 수, 0 <= F <= 48
A    = 요청당 최대 시도 횟수 = 2 (최초 1회 + 재시도 1회)
```

### 3.1 KMA APIHub

정상 슬롯마다 대상자 500m 지점 5개와 전국 특보 1개를 호출한다.

```text
APIHub 기본 호출/일
= R × (U500 × P + W)
= 48 × (5 × 1 + 1)
= 288

APIHub 재시도 포함 절대 상한/일
= 288 × A
= 576
```

| APIHub 작업                       | 슬롯당 | 하루 48슬롯 | 전 요청 1회 재시도 |
| --------------------------------- | -----: | ----------: | -----------------: |
| 500m `ta_chi,ta,hm` 지점 다중요소 |      5 |         240 |                480 |
| 폭염 특보현황 신형                |      1 |          48 |                 96 |
| 합계                              |      6 |     **288** |            **576** |

전체영역 `ta_chi` 한 번을 받는 대안은 특보를 포함해 `48 × (1 + 1) = 96회/일`이지만 응답 크기와 파싱 비용이 크다. P0-07에서 선택한 기본 경로는 대상자 5곳의 지점 다중요소 240회와 특보 48회다.

### 3.2 공공데이터포털 단기예보 폴백

500m 1차 소스가 실패한 슬롯에만 고유 5km 격자 3개를 조회한다.

```text
Data.go 폴백 호출/일 = F × U5 × 1 = F × 3
0 <= Data.go 폴백 호출/일 <= 48 × 3 = 144

Data.go 재시도 포함 절대 상한/일 = 144 × A = 288
```

| 폴백 슬롯 `F` | 공급자 호출 | 의미                      |
| ------------: | ----------: | ------------------------- |
|             0 |           0 | 1차 소스가 하루 종일 정상 |
|             1 |           3 | 한 슬롯만 세 격자 폴백    |
|            24 |          72 | 하루 절반의 슬롯에서 폴백 |
|            48 |     **144** | 하루 모든 슬롯에서 폴백   |

단기예보 발표시각 기준 캐시를 추가하면 실제 공급자 호출은 더 줄 수 있지만, 계정 예산은 캐시가 전혀 적중하지 않는 144회/일을 기준으로 잡는다.

### 3.3 공급자를 합산하지 않는 이유

하루 모든 슬롯에서 1차 요청을 시도한 뒤 폴백까지 실행하는 보수적 외부 호출 합은 `288 + 144 = 432회`다. 그러나 APIHub와 공공데이터포털은 별도 인증·쿼터이므로 432회를 APIHub 20,000회 한도와 비교하지 않는다. 공급자별로 288회와 144회를 각각 관리한다.

## 4. 구현 불변식

배치 구현과 테스트는 다음 조건을 고정해야 한다.

1. KST 현재시각을 30분 단위로 내림한 `slotStartKst`에 분산 잠금 또는 유일 키를 두어 같은 슬롯의 배치가 두 번 실행되지 않게 한다.
2. APIHub 500m는 `obs=ta_chi,ta,hm` 한 요청으로 호출한다. 요소별 세 요청으로 분리하지 않는다.
3. 단기예보는 `(nx, ny, baseDate, baseTime)`으로 캐시하고 한 응답에서 `TMP`, `REH`를 함께 읽는다.
4. 대상자 좌표를 APIHub 격자 키로 중복 제거하고, 단기예보는 `(nx, ny)`로 별도 중복 제거한다. 500m와 5km 키를 섞지 않는다.
5. 재시도는 최초 호출을 포함해 최대 2회로 제한한다. 4xx는 재시도하지 않고, 429·timeout·5xx만 지수 백오프 대상으로 삼는다.
6. 호출량 metric에는 공급자, endpoint 별칭, 성공·실패, 시도 횟수만 기록한다. API 키, 전체 URL, 대상자 ID·좌표는 기록하지 않는다.
7. 시드 대상자 좌표가 바뀌면 아래 기준값을 자동 검사해 이 문서와 배포 예산을 함께 갱신한다.

```js
const runsPerDay = 48;
const unique500mPoints = 5;
const unique5kmGrids = 3;
const maxAttempts = 2;

const apiHubBase = runsPerDay * (unique500mPoints + 1);
const dataGoFallbackMax = runsPerDay * unique5kmGrids;

console.assert(apiHubBase === 288);
console.assert(apiHubBase * maxAttempts === 576);
console.assert(dataGoFallbackMax === 144);
console.assert(dataGoFallbackMax * maxAttempts === 288);
console.assert(apiHubBase * maxAttempts <= 20_000);
```

## 5. 배포 전 남은 쿼터 확인

| 검증 항목                    | 현재 판정 | 배포 게이트                                                            |
| ---------------------------- | --------- | ---------------------------------------------------------------------- |
| APIHub 요청 횟수 20,000회/일 | 충족      | 최대 576회/일을 넘으면 배포 실패                                       |
| APIHub 전송량 5GB/일         | 검증 필요 | 실제 지점·특보 응답의 raw byte 길이로 48슬롯과 재시도 상한을 계산      |
| 공공데이터포털 요청 한도     | 검증 필요 | 계정 화면의 일 한도가 기상 288회와 별도 의약품 예산의 합 이상인지 확인 |
| 중복 배치 방지               | 구현 필요 | 동일 30분 슬롯을 동시에 두 번 실행하는 통합 테스트 추가                |

P0-07의 고정 fixture 크기는 파서 테스트용이며 실제 네트워크 응답 용량의 증거로 사용하지 않는다. 전송량 검증은 응답 본문을 저장하거나 로그에 남기지 않고 바이트 수만 계측한다.
